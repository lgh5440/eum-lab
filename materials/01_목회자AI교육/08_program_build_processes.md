# 프로그램별 제작 과정과 교육 전달 포인트

이 문서는 강사가 사례를 설명할 때 사용할 "제작 과정 해설 노트"입니다. 단순히 결과물을 자랑하는 자료가 아니라, 아무것도 모르는 상태에서 AI 도구와 대화하며 어떻게 문제를 쪼개고, 초안을 만들고, 실패를 고치고, 검증 기준을 세웠는지 전달하는 데 목적이 있습니다.

표시 규칙:

- `[핵심]`: 반드시 전달할 메시지
- `[시연]`: 강의 중 보여주면 좋은 장면
- `[주의]`: 오해하거나 위험해질 수 있는 지점
- `[질문]`: 참여자에게 던지면 좋은 질문

## 전체 공통 흐름

모든 프로그램은 아래 순서로 설명하면 이해가 쉽습니다.

1. 사역 또는 운영 문제를 발견한다.
2. 그 문제를 작은 첫 버전으로 줄인다.
3. AI에게 역할, 대상, 상황, 제약, 산출물을 분명히 준다.
4. 초안을 만든다.
5. 실제 화면, 공간, 데이터, 로그로 확인한다.
6. 실패한 부분을 다시 프롬프트와 작업 지시로 바꾼다.
7. 안전, 저작권, 개인정보, 운영 책임을 사람이 검수한다.

[핵심] 바이브코딩은 "AI가 알아서 다 만드는 것"이 아니라 "목회자가 방향을 주고, AI가 초안을 만들고, 사람이 검증하는 반복"입니다.

## 1. DAVID 메타버스 성경학교

대표 위치:

- `E:\2026 메타버스 DAVID`
- `E:\2026 메타버스 DAVID\DavidAdventureWorldHub`
- `E:\2026 메타버스 DAVID\Roblox-Game-Template`

### 제작 목적

성경학교의 주제, 본문, 메시지, 활동을 Roblox 기반 메타버스 경험으로 바꾸는 것이 목적이었습니다. 아이들이 단순히 화면을 보는 것이 아니라, 허브에 들어가고, 안내판을 보고, 포털을 통과하고, 미션을 수행하며 말씀 메시지를 경험하도록 설계했습니다.

### 제작 과정

1. 성경학교 원자료를 분석했습니다.
   - 주제, 본문, 과별 메시지, 챈트, 활동 흐름을 추출했습니다.
   - 성경학교 원본 이미지를 그대로 재사용하지 않고, 내용 기반으로 AI 이미지를 새로 만들었습니다.

2. "교재"를 "공간"으로 번역했습니다.
   - 입장 공간
   - 안내판
   - 1과/2과/3과 포털
   - 미션 구역
   - 말씀 정리 구역
   - 마무리 공간

3. Roblox 허브를 만들었습니다.
   - 교회/허브 건물 구조
   - 포털
   - 공원/미로
   - 안내판과 포스터
   - 조명과 이동 동선

4. 미션형 경험을 붙였습니다.
   - 1과: 베들레헴 목동 미션, 양, 늑대, 사무엘 퀴즈, 하프 리듬게임
   - 2과: 엘라 골짜기, 골리앗, 물맷돌, 전투형 미션
   - 이후 확장 가능한 구조를 고려했습니다.

5. Rojo와 Roblox Studio를 연결했습니다.
   - `src`는 원본 코드
   - `tools`는 생성 도구
   - `generated`는 Roblox Studio에서 실행하거나 확인할 산출물
   - 이 구분은 "원본과 생성물 분리"를 가르치기에 좋습니다.

6. 시행착오를 고쳤습니다.
   - 이미지가 흰 패널로 보임
   - Decal id와 Texture id 차이
   - SurfaceGui가 벽 너머로 보임
   - 포스터 위치와 비율이 맞지 않음
   - 조명이 너무 어둡거나 과함
   - 거대한 스크립트가 커져 AI가 다루기 어려움

7. 검증을 넣었습니다.
   - 미로가 실제로 출구까지 이어지는지 테스트했습니다.
   - 기본 Python에서는 `numpy`가 없어 실패했지만, 번들 Python에서는 테스트가 통과했습니다.
   - 이 장면은 "AI 개발은 환경 검증이 필요하다"는 교육 포인트로 좋습니다.

### 전달할 중요한 포인트

- `[핵심]` 성경학교 콘텐츠는 PDF나 PPT에 머물 필요가 없습니다. 본문, 메시지, 활동은 공간, 미션, 상호작용으로 바뀔 수 있습니다.
- `[핵심]` AI 이미지는 원본 교재 이미지를 복제하는 도구가 아니라, 저작권을 존중하면서 새 시각 자료를 만드는 보조 도구로 사용해야 합니다.
- `[핵심]` Roblox 같은 도구는 화려해 보이지만, 실제 시간은 이미지 비율, 위치, 조명, 동선, 권한 같은 세부 검증에서 많이 듭니다.
- `[시연]` `DavidAdventureWorldHub\README.md`의 폴더 구조를 보여주면 `src`, `tools`, `generated`의 차이를 쉽게 설명할 수 있습니다.
- `[시연]` published experience 또는 Roblox Studio 화면을 보여주되, 전체 재생성 명령은 복사본에서만 다룹니다.
- `[주의]` 성경학교 원본 이미지를 그대로 쓰지 않았다는 점, 내용 사용은 확인했지만 이미지 자료는 AI로 새로 만들었다는 점을 분명히 말해야 합니다.
- `[주의]` `ResetAndRunFullHub` 같은 명령은 기존 월드를 지울 수 있으므로 강의 중 실수로 실행하지 않습니다.
- `[질문]` "우리 교회의 성경학교 자료를 공간으로 바꾼다면, 입구에는 무엇이 있어야 할까요?"

## 2. E:UM Family 공통 구조

대표 위치:

- `D:\Projects\Web`
- `D:\Projects\Web\_eum-family`

### 제작 목적

E:UM은 하나의 앱이 아니라 여러 사역 도구를 하나의 브랜드와 공통 구조로 묶은 프로젝트입니다. 캠프, 놀이, 사진, 학교/교육, 진로/재능 등 서로 다른 문제를 각각 작은 앱으로 나누되, 공통 로고, 푸터, 데이터, 브랜드 원칙을 공유하도록 설계했습니다.

### 제작 과정

1. "하나의 거대한 교회 플랫폼"이 아니라 "작은 앱 묶음"으로 나눴습니다.
   - 캠프 운영
   - 놀이형 학습
   - 사진 정리
   - 교육 관리
   - 진로/재능 안내

2. 공통 브랜드를 만들었습니다.
   - E:UM 이름
   - 로고
   - 슬로건
   - 공통 푸터
   - 앱 간 연결 구조

3. 공통 데이터의 단일 출처를 만들었습니다.
   - `_eum-family`가 공유 자산과 문서의 중심입니다.
   - 각 앱이 같은 정보를 손으로 따로 고치지 않도록 동기화 스크립트를 사용했습니다.

4. 앱별 배포 방식을 나눴습니다.
   - GitHub Pages
   - Firebase Hosting
   - Electron desktop app
   - 정적 HTML
   - React/Vite 앱

5. 공통 변경의 위험을 관리했습니다.
   - 공통 푸터 하나를 고쳐도 여러 앱에 영향이 갑니다.
   - 그래서 공유 작업 로그와 앱별 작업 로그가 필요했습니다.

### 전달할 중요한 포인트

- `[핵심]` 교회 앱을 만들 때 처음부터 "교회 전체 통합 플랫폼"을 만들려고 하면 실패 가능성이 커집니다. 작은 문제 하나를 해결하는 앱부터 시작하는 것이 좋습니다.
- `[핵심]` 앱이 여러 개로 늘어나면 공통 로고, 색상, 푸터, 문구, 링크를 어디에서 관리할지 정해야 합니다.
- `[핵심]` "공통 자산"과 "각 앱 고유 기능"을 분리하는 습관이 나중에 큰 혼란을 줄입니다.
- `[시연]` `_eum-family` 폴더와 각 앱 폴더가 분리된 구조를 보여주면, 비개발자도 "본사/지점" 구조처럼 이해할 수 있습니다.
- `[주의]` 공통 파일을 고치면 여러 앱에 영향이 가므로, 반드시 작업 로그와 검증이 필요합니다.
- `[질문]` "우리 교회의 사역 도구가 5개로 나뉜다면, 공통으로 유지해야 할 것은 무엇일까요?"

## 3. E:UM Camp

대표 위치:

- `D:\Projects\Web\eum-camp`

### 제작 목적

교회나 단체가 캠프, 수련회, 연합행사를 운영할 때 필요한 참가자 관리, 교회별 신청, 조 편성, 현장 체크, 문서 출력, 운영 대시보드를 제공하는 앱입니다.

### 제작 과정

1. 실제 현장 운영 업무를 화면으로 나눴습니다.
   - 참가자 목록
   - 교회별 신청 현황
   - 조/방/차량 배정
   - 현장 체크인
   - 문서 출력
   - 운영 대시보드

2. 처음에는 가상 데이터를 넣어 실제 화면처럼 보이게 했습니다.
   - 실제 개인정보를 넣지 않고도 운영 흐름을 테스트할 수 있었습니다.
   - 교육에서는 이 점이 매우 중요합니다.

3. React/Vite/Firebase 기반으로 앱을 구성했습니다.
   - 브라우저에서 실행
   - Firebase Hosting 배포
   - Firestore를 통한 온라인 공동 사용 가능성

4. 운영 문서를 만들었습니다.
   - AI 설치 가이드
   - 수동 설치 가이드
   - Firebase 배포 가이드
   - 현장 모바일 사용 안내

5. 보안과 권한 문제를 점검했습니다.
   - 인증 사용자라면 너무 넓게 읽고 쓸 수 있는 규칙은 위험합니다.
   - 공개 배포 전 Firestore 규칙 검토가 필요합니다.

### 전달할 중요한 포인트

- `[핵심]` 실제 행사를 앱으로 만들 때는 "멋진 디자인"보다 "운영자가 오늘 쓸 수 있는가"가 먼저입니다.
- `[핵심]` 실습과 시연에는 반드시 가상 데이터를 사용해야 합니다.
- `[핵심]` 캠프 앱은 참가자 관리처럼 개인정보가 얽히기 때문에, AI에 실제 명단을 넣으면 안 됩니다.
- `[시연]` 대시보드, 참가자 목록, 조 편성 화면을 보여주면 목회자들이 바로 필요를 느낄 수 있습니다.
- `[주의]` Firebase 같은 온라인 DB를 붙이면 권한 규칙이 핵심입니다. "작동한다"와 "안전하다"는 다릅니다.
- `[질문]` "우리 교회 수련회 준비에서 매년 반복되는 엑셀 작업은 무엇인가요?"

- `[주의]` 어린이 대상 활동은 재미 요소가 말씀 메시지를 덮지 않게 해야 합니다.
- `[질문]` "우리 교육 활동 중 버튼 세 개와 결과 화면 하나로 바꿀 수 있는 것은 무엇인가요?"

## 5. E:UM School

대표 위치:

- `D:\Projects\Web\eum-school`
- `D:\Projects\Web\eum-school-v5`

### 제작 목적

교회학교나 교육 프로그램의 학생, 교사, 반, 출석, 활동 흐름을 관리하는 방향의 앱입니다. 아직 기획/검증 단계 성격이 강하므로, "완성 사례"보다 "복잡한 교육 시스템을 어떻게 쪼개야 하는가"의 사례로 설명하는 것이 좋습니다.

### 제작 과정

1. 학생/교사/관리자 역할을 나눴습니다.
2. 출석, 반 관리, 활동 기록 같은 기능 후보를 정리했습니다.
3. 정적 프로토타입 또는 Supabase/Firebase 기반 구조를 실험했습니다.
4. 공개 등록, 권한, Auth 연결 같은 민감한 부분을 점검했습니다.
5. Mock 데이터와 실제 데이터를 구분하는 문제가 드러났습니다.

### 전달할 중요한 포인트

- `[핵심]` 교육 관리 앱은 기능보다 권한 설계가 먼저입니다. 학생, 교사, 관리자, 보호자가 보는 정보가 달라야 합니다.
- `[핵심]` 처음부터 실제 학생 데이터를 넣지 말고, mock 데이터로 화면과 흐름을 확인해야 합니다.
- `[주의]` 공개 등록 화면이나 첫 관리자 생성 흐름은 배포 전에 반드시 막거나 보호해야 합니다.
- `[시연]` "학생/교사/관리자 역할표"를 화이트보드로 그리면 비개발자도 구조를 이해합니다.
- `[질문]` "우리 교회학교 데이터 중 교사만 봐야 하는 것과 전체가 봐도 되는 것은 무엇인가요?"

## 6. E:UM Photo

대표 위치:

- `D:\Projects\Web\eum-photo`

### 제작 목적

행사 사진을 정리하고, 분류하고, 필요한 형태로 관리하는 데 초점을 둔 데스크톱 앱 성격의 프로젝트입니다. 교회 현장에서 사진은 많지만 정리와 공유, 보관 기준이 약한 경우가 많기 때문에 교육 사례로 적합합니다.

### 제작 과정

1. 행사 사진 정리 문제를 정의했습니다.
   - 사진이 너무 많음
   - 누가 찍었는지 모름
   - 공유용/보관용/삭제용 구분이 어려움
   - 아이들 얼굴이 포함되어 안전 기준이 필요함

2. Electron/React 기반 데스크톱 앱 방향으로 잡았습니다.

3. 파일 선택, 복사, 분류, 저장 같은 로컬 파일 기능이 필요했습니다.

4. 데스크톱 앱에서는 파일 접근 권한이 큰 위험이 됩니다.
   - 너무 넓은 파일 읽기/쓰기 권한은 위험합니다.
   - 선택한 폴더 안에서만 작업하도록 제한해야 합니다.

### 전달할 중요한 포인트

- `[핵심]` 교회 사진 앱은 편리함보다 개인정보와 초상권 기준이 먼저입니다.
- `[핵심]` 데스크톱 앱은 웹앱보다 파일 접근 권한이 강하므로 더 조심해야 합니다.
- `[시연]` 사진 폴더를 "원본, 선별, 공유, 보관"으로 나누는 흐름을 보여주면 실무자들이 바로 이해합니다.
- `[주의]` 아이들 얼굴이 포함된 사진은 AI 도구에 함부로 업로드하지 않습니다.
- `[질문]` "우리 교회는 행사 사진을 몇 년 보관하고, 누가 삭제를 결정하나요?"

## 9. Sperma

대표 위치:

- `D:\Projects\Sperma`

### 제작 목적

KIS REST API와 Upbit API 기반의 자동매매 시스템입니다. 이 교육에서는 투자 방법이나 금융 조언으로 다루지 않고, AI로 만든 복잡한 시스템을 어떻게 검증하고 운영 기준을 세우는지 보여주는 사례로만 사용합니다.

### 제작 과정

1. 시장과 전략을 나눴습니다.
   - 국내 분봉
   - 국내 일봉
   - 미국 주식
   - 코인

2. 백테스트를 반복했습니다.
   - 여러 전략 파일과 파라미터를 실험했습니다.
   - 성과 지표와 위험 지표를 같이 봤습니다.

3. 챔피언 전략을 골랐습니다.
   - 아무 결과나 바로 실거래로 보내지 않았습니다.
   - 검증 기준을 통과한 전략만 다음 단계로 넘겼습니다.

4. 페이퍼 단계를 거쳤습니다.
   - 실제 돈을 쓰기 전에 모의 운영으로 확인합니다.
   - 교회 앱으로 치면 실제 명단을 넣기 전 가상 데이터로 운영하는 단계입니다.

5. LIVE 운영에는 안전 게이트를 두었습니다.
   - dry-run
   - live-confirmed
   - 주문 파일
   - 손실 한도
   - 스케줄러
   - 토큰 상태

6. 로그와 리포트를 남겼습니다.
   - 무슨 일이 일어났는지 나중에 추적할 수 있어야 합니다.

### 전달할 중요한 포인트

- `[핵심]` Sperma의 교육 가치는 "자동매매"가 아니라 "검증 문화"입니다.
- `[핵심]` AI가 만든 코드가 실제 세계에 영향을 주면, 반드시 백테스트, 샘플 데이터, 페이퍼 운영, 승인 절차가 필요합니다.
- `[핵심]` 교회 앱도 똑같습니다. 실제 아이들, 교인, 돈, 개인정보에 닿기 전에 반드시 작은 테스트 단계를 거쳐야 합니다.
- `[시연]` 파일 구조에서 `reports`, `logs`, `config`, `scripts`, `interface` 같은 폴더 이름만 보여줘도 운영 체계를 설명할 수 있습니다.
- `[주의]` 실거래, 토큰, 계좌, 주문 관련 화면이나 파일은 교육 중 열지 않는 것이 좋습니다.
- `[주의]` 이 사례는 금융 조언이 아니라 안전한 AI 시스템 운영의 사례입니다.
- `[질문]` "우리 교회 앱에서 Sperma의 dry-run에 해당하는 안전한 테스트 단계는 무엇일까요?"
