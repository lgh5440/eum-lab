## HTML·CSS·JavaScript — 집 짓기 비유

**【화면 — 집 짓기 비유 표】**
```
HTML       = 뼈대 (벽, 문, 방 배치)     → 명함에서는 "여기에 이름, 여기에 버튼"
CSS        = 꾸미기 (페인트, 가구, 조명)  → 글자 크기, 색깔, 위치
JavaScript = 움직임 (스위치, 자동문)     → 누르면 전화가 걸린다
```

> "집을 짓는다고 생각해보세요. HTML은 뼈대입니다 — 벽이 어디 있고, 문이 어디 있고, 방을 어떻게 배치할지. 우리 명함으로 치면 '여기에 이름을 놓고, 여기에 버튼을 놓는다'는 겁니다."

> "CSS는 꾸미기입니다 — 페인트칠하고, 가구 놓고, 조명 다는 것. 명함에서는 글자 크기, 색깔, 위치를 정하는 부분입니다."

> "JavaScript는 움직임입니다 — 스위치를 누르면 불이 켜지고, 자동문이 열리는 것. 명함에서는 버튼을 누르면 실제로 전화가 걸리는 그 동작입니다."

## 프론트엔드 / 백엔드 — 매장 비유

## 바이브코딩이란?

**【화면 — 정의】**
```
바이브코딩 =
AI에게 글만 쓰게 하지 않고, 프로그램을 만들게 하는 것
```

> "AI는 텍스트만 만드는 게 아니라, 실제로 작동하는 웹페이지, 프로그램까지 만들 수 있습니다. 이걸 코딩을 몰라도 대화로 만든다고 해서 '바이브코딩'이라고 부릅니다."

## 블록코딩

> "혹시 '블록코딩'이라는 말도 들어보셨을 겁니다. 스크래치처럼, 미리 만들어진 블록을 끼워 맞춰서 프로그램을 만드는 방식입니다. 코드를 직접 타이핑하지 않고 블록을 조립하는 거라, 아이들 코딩 교육에 많이 쓰입니다. 오늘 우리가 할 바이브코딩과는 방식이 다르지만, '코드를 직접 안 써도 뭔가를 만들 수 있다'는 점은 같습니다."

## 모듈코딩

> "그리고 '모듈코딩'이라는 말도 있습니다. 한 번에 다 만들지 않고, 기능별로 나눠서 하나씩 만드는 방식입니다. 예를 들면 명함을 만들 때도 이름 바꾸기, 색깔 바꾸기, 링크 정리하기를 한 번에 몰아서 시키지 않고 하나씩 나눠서 시키는 것 — 이게 모듈코딩입니다. 이 방식, 이따 실습에서도 그대로 쓰실 거고, 이따 제 실수담에서도 계속 나올 겁니다."

### 마무리

## ⑥ 이 외에 AI가 목회에서 하는 것들 (짧게, 약 1분)

# 6부 (52~67분) — 실수 경험담 15분

**진행 원칙**: 각 실수당 약 2분. "이렇게 하면 헤매고, 이렇게 하면 빨리 된다" **대구(對句) 형식**으로 진행 — 매번 같은 리듬을 반복해서 청중이 패턴에 익숙해지게 한다. **방금 실습을 직접 해보셨기 때문에, 각 실수를 방금 겪은 경험과 연결해서 짚어드립니다.**

1. 실수 제목 제시
2. "저는 이렇게 했습니다" (실패 상황 묘사)
3. (있는 경우) 실제 사건 보강

# 7부 (67~78분) — 올바른 바이브코딩 사용법 + 앞으로 갈 길 11분

## 앞부분: 원칙 (약 5분)

> "방금 7가지 실수를 말씀드렸는데요, 이제 그 실수들에서 뽑아낸 원칙을 정리해드리겠습니다."

**【화면 — 원칙 문구】**
```
코딩은 누구나 할 수 있지만, 잘 아는 사람이 잘 사용할 수 있습니다.
```

> "코딩은 이제 누구나 할 수 있습니다. AI가 다 해주니까요. 그런데 그걸 '잘' 쓰는 건 다른 문제입니다. 경험이 많은 누군가가 6하원칙에 맞춰 생각하면 좋은 결과가 나옵니다. 이게 아까 실수③에서 말씀드린 '목적+상황+원하는 결과+제한조건' 공식이고, 바로 이게 '코딩적 사고'입니다."

> "그리고 아까 4부·실수①에서 말씀드린 모듈식 코딩 — 큰 일을 한 번에 시키지 않고 기능별로 나눠서 하나씩 만드는 것. 이 두 가지, 코딩적 사고와 모듈식 코딩이 실제로 AI를 잘 쓰는 사람과 못 쓰는 사람을 가르는 핵심입니다."

> "이걸 세 갈래로 다시 정리하면 이렇습니다."

**【화면 — 세 갈래】**
```
질문법     목적 + 상황 + 원하는 결과 + 제한조건
자료 다루기  모르는 영역 → AI 먼저 / 아는 영역 → 내 생각 먼저 정리 후 AI
검증       원문 확인 + 출처 재확인
```

> "여러분이 잘 모르는 분야는 AI에게 먼저 물어봐도 괜찮습니다. 그런데 신학이나 설교처럼 여러분이 이미 잘 아시는 영역은, 여러분의 생각을 먼저 정리한 다음에 AI에게 다듬어달라고 하는 순서로 가셔야 합니다. 순서가 바뀌면 AI가 여러분의 생각을 오히려 흐리게 만듭니다."

> "이 세 가지 — 질문법, 자료 다루기, 검증 — 이 조합이 되면, 여러분은 이제 AI를 '그냥 물어보는 도구'가 아니라 '일을 맡길 수 있는 직원'으로 쓰실 수 있게 됩니다."

**【화면 — 5원칙, 한 슬라이드】**
```
① 작게 시작한다
② 목적을 정확히 말한다
③ AI에게 현재 상황을 먼저 보게 한다
④ 한 번에 하나씩 수정한다
⑤ 결과는 사람이 검증한다
```

> "오늘 90분 중에서 딱 하나만 기억하고 가셔야 한다면, 이 다섯 가지입니다. 이것만 기억하시면, 오늘 제가 겪었던 시행착오의 상당 부분을 건너뛰실 수 있습니다."

**⚠️ 발표자 지시 — 도입 멘트 (반드시 그대로/취지를 살려서 말할 것)**:

- **하네스**: "AI가 혼자 일할 수 있게 감싸주는 틀입니다. AI에게 도구를 쥐어주고, 일을 시키고, 결과를 확인하고, 다시 시키는 과정을 반복해주는 프로그램입니다."

# 부록: 발표자 참고자료 (강의 본편에는 포함되지 않음 — 필요시 애드리브·질문 답변용)

> 이 부록은 `tips_reference.md`를 정리한 것입니다. 위 90분 대본에는 직접 편입되어 있지 않으며, 시간이 남거나 관련 질문이 나왔을 때 발표자가 참고용으로 쓰는 자료입니다. 아래 내용은 모두 출처가 있는 참고자료이며, 발표 시 슬라이드에 넣을지는 별도로 결정합니다.

## 부록 1. 클로드 / 코덱스 — 데스크탑 vs 웹, 뭐가 더 나은가

**결론**: "가벼운 작업은 웹, 몰입해서 만들 땐 데스크탑."

| | 웹(claude.ai) | 데스크탑 앱 |
|---|---|---|
| 설치 | 필요 없음, 링크만 열면 됨 | 설치 필요 |
| 할 수 있는 것 | 대화, Projects, Skills, 웹검색, 리서치, 파일 생성 | 위 전부 + MCP 연결(내 컴퓨터 파일·도구와 직접 연결), 로컬 파일 직접 접근, Cowork(에이전트 모드), Quick Entry, 창 하나에 여러 세션 동시 실행 |
| 최근 변화 | 2026.7.7부터 Cowork(에이전트 모드)가 웹에서도 됨(Max 플랜 우선) | Code 탭에 내장 브라우저까지 들어옴(2026.7 출시) |

**질문 답변용 문장**: "오늘처럼 짧게 뭔가 물어보고 답 받을 땐 웹으로 충분합니다. 그런데 컴퓨터에 있는 내 파일을 직접 만지고, 만든 걸 바로 배포까지 하려면 데스크탑 앱(또는 Claude Code)이 훨씬 편합니다. 오늘 라이브 데모가 바로 그 데스크탑/Claude Code 수준을 보여드린 겁니다." 코덱스(OpenAI)도 구조가 비슷합니다 — ChatGPT 웹 안에도 코드 실행 기능이 있고, 별도 설치하는 Codex CLI가 있습니다. "가볍게 물어볼 땐 웹, 진짜 프로젝트를 굴릴 땐 CLI/데스크탑" 원칙은 동일합니다.

*Sources: Claude Desktop App Guide 2026 / Claude on the Desktop: What the App Adds Over the Browser / Claude Cowork on the Web*

## 부록 2. "AI를 더 깊이 쓰는 단계" — 개인 여정 예화 (7부 뒷부분 보강용)

7부의 "앞으로 갈 길"을 더 풀어서 설명해야 할 때 쓸 수 있는 4단계 구조:

```
1. 혼자 쓰는 AI 채팅        (오늘 이 강의 수준 — 여러분이 오늘 배우는 것)
2. AI가 붙은 코드 에디터     (VS Code, Cursor, Antigravity — "AI가 옆에서 코드를 같이 봐준다")
3. 한 도구에 여러 AI 모델 연결 (어떤 모델이 이 작업엔 더 나은지 실험)
4. 여러 AI가 역할을 나눠 협업 (관리자 AI가 실무 AI들에게 일을 나눠주고 검토)
```

질문이 나오면: "저도 VS Code에서 시작해서 Antigravity, Cursor를 거쳐, 한 툴에 AI 2~3개를 연결해 분업을 시도하다가 지금은 이 4번 단계까지 실험하고 있습니다."

## 부록 3. 크롬 확장 프로그램 — 질문 시 답변용

**결론**: 다 설치하지 말 것. 확장 프로그램을 욕심껏 깔면 브라우저가 느려지고 결정 피로만 늘어난다는 게 2026년 여러 테스트의 공통 결론. 하나만 골라 써보고 시간이 절약되는 걸 확인한 뒤 하나씩 늘릴 것 — 이것도 실수①("한 번에 다 갖추려 함")과 같은 원칙.

- **Perplexity 확장** — 출처가 달린 답변을 검색창에서 바로 받음. 설교 자료·통계 조사에 유용.
- **Gemini in Chrome** — 크롬 기본 내장 AI. 여러 탭 비교, 유튜브 영상 내용 질문 등.
- **Sider AI** — 사이드바에서 Claude/GPT/Gemini 등 여러 모델을 한 번에 비교. "AI 2~3개 연결해서 써보기"를 브라우저 차원에서 가장 쉽게 흉내내는 도구.
- (참고) Grammarly는 영어 전용이라 한국어 설교/공지문 교정에는 큰 도움이 안 됨 — 추천에서 제외.

*Sources: 10 best AI Chrome extensions for productivity in 2026 / Best AI Extensions for Chrome in 2026*

## 부록 4. 강의 준비 중 실제로 있었던 일 — 예비 예화

이 대본을 준비하는 과정에서 발표자가 실제로 겪은 일: NotebookLM 로그인이 갑자기 안 돼서, 재부팅만 반복하지 않고 원인을 하나씩 추적했더니 좀비 크롬 프로세스 24개가 쌓여있었던 것을 찾아 정리한 경험. 이 강의를 만드는 과정 자체가 "실수②(결과가 이상하면 처음부터 다시 만들기보다, 원인을 먼저 확인)"의 실시간 사례가 될 수 있음 — 시간이 남거나 관련 질문이 나오면 짧게 소개 가능. *(본편 대본에는 편입하지 않음 — 필요시 발표자 재량으로 추가)*

## 부록 5. 네이버·카카오맵 지도 정보 vs 링크 페이지 — 질문 시 답변용

| | 네이버·카카오맵 지도 정보 | 링크 페이지 |
|---|---|---|
| 누가 보나 | "우리 동네 교회" 검색하는 처음 보는 사람(발견용) | 이미 아는 성도님·지인에게 공유(안내용) |
| 담을 수 있는 것 | 주소·운영시간·사진·웹사이트 링크 등 정해진 항목만 | 설교·헌금·개인 연락처 등 원하는 건 뭐든 |
| 디자인 | 네이버가 정한 틀 그대로 | 우리 교회만의 색·구성 |
| 리뷰 | 아무나 남길 수 있음(리스크) | 없음(우리가 원하는 내용만) |

**팁 문구 (질문 나오면 사용)**: "우리 교회가 네이버·카카오맵에 이미 등록돼 있는지 검색해보세요. 없으면 무료로 등록하고, 있으면 정보가 최신인지 확인한 다음, 웹사이트 칸에 오늘 만든 링크를 넣어주세요. 지도에서 발견 → 링크 페이지에서 설교·헌금·연락처까지 이어지는 흐름이 완성됩니다." *(실습 시간에는 다루지 않기로 결정됨)*

## 부록 6. 목회에서 바로 쓰는 AI — 8가지 활용 목록 (5부 ⑥에서 언급, 상세는 이 자료로)

> 5부 실습 마지막에 "이런 것들도 됩니다, 목록은 자료로 드리겠습니다"라고 짧게 언급하고 넘어가는 전체 목록입니다.

```
· 설교 개요 잡기
· 성경 본문 연구 자료 정리
· 교회학교 공과 준비
· 여름성경학교 프로그램 구성
· 활동지 제작
· 포스터·이미지 만들기
· 공지문 작성
· 논문 목차·선행연구 정리
```

**간단한 설명 (질문 나오면 참고)**:
- 설교 개요 — 본문을 주고 구조를 잡아달라고 하면 초안이 나옵니다.
- 성경 본문 연구 — 관련 자료를 정리해달라고 하면 흩어진 자료를 모아줍니다.
- 교회학교 공과·여름성경학교 프로그램 — 대상 연령과 주제를 주면 틀을 짜줍니다.
- 활동지·포스터·공지문 — 이런 반복적인 문서 작업에 특히 시간을 아껴줍니다.
- 논문 목차·선행연구 정리 — 다만 AI가 준 것은 초안이므로, 6부 실수④에서 말씀드린 것처럼 검증이 필요합니다.
